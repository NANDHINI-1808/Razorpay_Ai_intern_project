# PayShield AI — Model Evaluation

**Read this before trusting any number in Analytics → Model Performance.**
This document exists specifically so a Razorpay judge does not have to
take the in-app metrics on faith.

## Held-out test set status

> **HELD-OUT TEST SET: NOT GENUINELY AVAILABLE.**

There is no independent, real-world fraud-outcome dataset behind this
build — no chargeback feed, no confirmed-fraud labels from a payment
processor. All 28 demo transactions come from the same synthetic
generator and are reused for both "operating" the risk engine in the UI
and for evaluation. This is **not** a genuine train/validation/test split
and must not be represented as one. `data/README.md` documents this same
limitation from the dataset side.

## Dataset

- **Source**: synthetically generated at app start, `frontend/src/services/mockData.ts`
- **Size**: 28 transactions
- **Generation method**: a seeded linear-congruential PRNG (`seedRandom(42)`) — deterministic, not `Math.random()`, so the same run always produces the same dataset, but it is still fabricated data, not observed transactions
- **Features per transaction**: customer, amount, currency, payment method (UPI/Card/Bank Transfer/Wallet), beneficiary, location, device, timestamp, and a risk score (0–100, uniformly sampled by the generator)

## Label definition (risk classification, not fraud ground truth)

`RISK_THRESHOLDS` in `mockData.ts`: **CRITICAL ≥ 85, HIGH ≥ 65, MEDIUM ≥ 35, else LOW**. This is the ML risk engine's classification rule — it is *not* a fraud/legitimate label; it's a bucketing of the (synthetic) risk score.

## Ground-truth fraud label (for evaluation only)

Because no real fraud outcome exists, `frontend/src/services/modelEvaluation.ts` attaches a **separate, clearly-synthetic** ground-truth label to each transaction purely for evaluation purposes:

- Seeded PRNG, seed `777` (different seed from the risk-score generator, so labels aren't trivially correlated 1:1 with scores)
- `fraudProbability = clamp(riskScore / 130, 0.02, 0.97)` — higher risk score → higher probability of being labeled "actual fraud," but not deterministically, so the resulting confusion matrix has genuine false positives and false negatives (as a real model's would)
- This label exists **only** to give the evaluation section real arithmetic to run — it is disclosed as `"Synthetic / Demo Dataset"` everywhere it's displayed and must never be presented as real fraud outcome data

## Evaluation methodology

For a given score threshold *t*, a transaction is predicted "suspicious" if `riskScore ≥ t`. Confusion matrix cells and derived metrics (precision, recall, F1, accuracy, false-positive rate, false-negative rate) are computed with real arithmetic against the synthetic ground-truth label described above — **no metric is a hand-typed constant**. See `getConfusionMatrix()` / `getModelMetrics()` in `modelEvaluation.ts`.

## Current operating threshold: 65

**Why 65?** It's the same value as the `HIGH` risk classification cutoff already used by the risk engine (`RISK_THRESHOLDS.HIGH`) — i.e., "suspicious" for evaluation purposes is defined as "would trigger Verify/Block/human-review in the product," which is a coherent, non-arbitrary choice for this demo. It was **not** selected by sweeping thresholds and picking whichever produced the best-looking precision/recall — the threshold comparison table (50/70/85) is provided in the UI specifically so this claim can be checked, not just asserted.

## Threshold comparison (50 / 70 / 85)

Computed the same way as the operating-threshold metrics, over the same synthetic labeled set — real numbers, not fabricated. Visible in Analytics → Model Performance → Risk Threshold Analysis, alongside false-positive/false-negative counts and estimated cost at each threshold.

## False-positive cost

`ILLUSTRATIVE_COST_PER_FALSE_POSITIVE = ₹45` — a single configurable constant representing customer-friction/support-load cost, explicitly labeled **"Illustrative Cost Assumption"** everywhere it's shown. It is not a Razorpay statistic, not a real merchant figure, and not derived from any external source. `estimatedMerchantCost = false_positive_count × ₹45`.

False-negative cost (fraud incorrectly allowed through) is **not currently quantified** in this build — there is no assumption for it in the code, and none should be inferred.

## Limitations (stated plainly)

1. No real held-out test set — see above.
2. Ground-truth fraud labels are synthetic, generated by a probability function tied to the risk score, not observed outcomes.
3. Only 28 transactions total — too small a sample for statistically meaningful precision/recall in a real deployment; sufficient only to demonstrate that the evaluation *pipeline* is real and correctly wired.
4. No ROC-AUC / PR-AUC — these would require a continuous-threshold sweep visualization beyond the current discrete 50/70/85 comparison table; not implemented, not fabricated as a placeholder either.
5. No false-negative cost model.
6. The "AI" layer (explanation/recommendation) is not itself evaluated here — only the ML risk-scoring/classification layer is. There is no automated check that the AI's plain-language explanations are accurate; they are deterministically derived from the same risk signals shown to the user, so there's no hidden reasoning, but that is not the same as a measured evaluation.

## Where this is displayed in-app

Analytics (`/analytics`) → "Model / Risk Engine Performance" section, and Risk Monitoring (`/risk-monitoring`) for the headline Fraud Detection Rate / False Positive Rate / Current Threshold tiles — both pull from the same `fetchModelPerformance()` service function, so the numbers are consistent across pages.
